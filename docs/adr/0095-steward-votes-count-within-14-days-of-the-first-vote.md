# 0095. Steward votes count within 14 days of the first vote

- Status: Accepted
- Date: 2026-11-16
- Supersedes: only the wording of ADR 0023 point 3 ("within `stewardProposalDays` (14) of each other"), which ADR 0027 point 4 carried forward as "a proposal expires after 14 days". It makes that expiry precise. Everything else in 0023, 0027 and 0029 stands.

## Context

ADR 0023 point 3 said a steward change takes effect when enough distinct stewards vote "within 14 days of each other", and ADR 0027 point 4 kept that as "a proposal expires after 14 days". The shared `StewardRules` read it as a sliding window: for every vote it counted the distinct voters dated from that vote to 14 days after it, and the change took effect if any such span reached the quorum. So a proposal never really expired. With a quorum of 3, votes on days 0, 10 and 20 were pending, but the day-0 steward voting again on day 21 made it take effect at once (days 10, 20 and 21), although the proposal had opened three weeks earlier.

The circle-rule votes (`config.update`, ADR 0051) and category votes (`tag.change`, ADR 0086) already worked differently. A proposal opens with its first vote, a later vote joins it only while it is no more than 14 days after that first vote, and a vote after that starts a new proposal and drops the old votes. So three kinds of steward vote followed one rule and the other three followed another. On 2026-11-16 the owner decided that steward votes follow the circle-rule and category rule.

## Decision

1. **One window for every steward vote.** A proposal for one subject (add this member, remove this member, or these exact steward settings) opens with its first vote. A later vote for the same subject joins it if the later vote's day is no more than 14 days (`DEFAULT_STEWARD_PROPOSAL_DAYS`) after the first vote's day. The 14th day is included: first vote on day 0, last joining vote on day 14. A vote after that starts a new proposal, with itself as the first vote, and the earlier votes no longer count. The change takes effect when the open proposal has the required number of distinct current stewards (the target excluded for a removal), as before.
2. **Order.** Votes are taken in log order (`serverSeq` on the server, place in the log in a client), as `config.update` and `tag.change` already are. The "first vote" is the first one in the log since the subject was last decided, not the earliest date.
3. **One implementation.** `ProposalWindow.isOpen(firstDay, day)` (in `StewardQuorum.kt`) is the window test for all five vote types (`steward.add`, `steward.remove`, `steward.policy`, `config.update`, `tag.change`). `StewardRules.currentProposal(votes)` gives the votes of the open steward proposal. The server (`EventRules`), every client fold (`CircleFold`, `MarketFold`) and the app's pre-check and Stewards page (`CircleApp`) all use them, so they cannot drift apart.
4. **The inactivity fallback (ADR 0027 point 6) is not changed by the window.** Its "earliest matching event" stays the proposer's earliest vote for that subject since the subject was last decided, even when the vote count has since restarted. Two reasons. The fallback is not a vote count: it is the proposer repeating a change while every other steward stays silent, and any event from another steward still cancels it. Its delay can be up to 90 days (ADR 0027, 0029), so measuring it from the first vote of the current 14-day proposal would make every delay over 14 days impossible, and the default 14-day delay would work on exactly one day. We considered measuring from the first vote of the current proposal and rejected it for that reason.
5. **No schema change.** The server keeps every pending vote in `steward_votes` as before, with its `server_seq`, and clears a subject's votes when the change takes effect. Votes from an expired proposal stay stored. The quorum count ignores them and only the fallback reads them (point 4).
6. **What members see.** The Stewards page lists a proposal only while its window is open (until the first vote's day plus 14). It counts only the votes of the open proposal, and it offers Agree to a steward whose vote belonged to an expired proposal. The page shows no "days left" line for any of the three proposal kinds, so no wording changes.

## Consequences

- A steward proposal really expires 14 days after its first vote, the same as circle rules and categories, so stewards learn one rule. A late vote is not lost: it opens a new proposal that the others can agree to within its own 14 days.
- A change can no longer be completed weeks after it was proposed by mixing old and new votes. Some changes that used to take effect now need the others to vote again. Logs built under the old rule could fold differently: a steward change that took effect only through the sliding window would now stay pending. There are no live circles yet, so this is accepted. The server and the clients change together, so they still agree with each other.
- The fallback works as before, including delays longer than the window.
- Tests: `StewardRulesTest` (votes on days 0, 10, 20 and then 21 stay pending and the open proposal holds only the day-20 and day-21 votes; days 0, 14, 14 take effect; days 0, 14, 15 do not; log order; a restarted settings proposal; the fallback after a restarted proposal, with the default delay and a 30-day one), `CircleFoldContract` (JVM and JS: an add and a settings change that restart), server `StewardTest` (two tests, including that old votes stay stored) and a real-server app test (the proposal is shown on its 14th day, gone on the 15th, and a new vote opens a new one).
